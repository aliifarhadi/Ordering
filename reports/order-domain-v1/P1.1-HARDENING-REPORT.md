## 2. Fix 1 — completion is derived from the required service scope

`IssueOrderService` previously returned the whole operation as Confirmed whenever `tickets.Count > 0` for the OperationId. That is wrong for a multi-traveler Order.

Completion is now computed as:

```
requiredServiceIds   = services requiring a document, not cancelled
documentedServiceIds = non-void coupons persisted against the Order
outstanding          = required − documented
```

The operation is Confirmed **only** when `outstanding` is empty. `outstanding` is returned on the result (`IssueOrderOutcome.OutstandingServiceIds`) so a caller can see exactly what is unresolved. `tickets.Count` is no longer used as completion evidence anywhere.

## 3. Fix 2 — the same document attempt is recovered, never re-issued

Per traveler/document role the service now distinguishes the two cases explicitly:

- **no prior attempt** → allocate a controlled number, persist the allocation (durable before dispatch), then `IssueAsync` with the stable provider key `issue:{travelerId}:{operationId}`;
- **prior unresolved attempt** (an allocation for the same `OperationId` + role still in state `Reserved`) → **no new number, no new ticket, no new operation** — `RecoverAsync` is called with the same OperationId, the same provider key and the same document number.

`DocumentStock.FindAllocation(operationId, role)` was added for that lookup.

## 4. Fix 3 — safe partial-issuance outcomes

| Case | Behaviour now |
|---|---|
| A confirmed, B confirmed | tickets/coupons persisted, allocations `Issued`, issued-document evidence applied to the Order, operation `Completed`, receipt `Completed`, claim resolved, result Confirmed |
| A confirmed, B **Pending** | A's ticket preserved, B's allocated number preserved as `Reserved`, result is **not** Confirmed, operation `AwaitingExternal`, receipt `Pending`, **claim not released**; a retry recovers B only |
| A confirmed, B **Unknown** | as above but receipt `Unknown`; recovery investigates B on the same document/operation, no blind retry, no replacement number |
| A confirmed, B **Rejected** | operation `NeedsReconciliation`, receipt `NeedsReconciliation`, **claim retained**; A's ticket is preserved and is **not** voided; no compensation was invented |
| B rejected before any success | operation `Rejected`, receipt `Rejected`, allocation `Retired` (never recycled), claim resolved — safe because no irreversible document exists |

A residual outstanding scope after the loop also resolves to `NeedsReconciliation` rather than a false Confirmed.

## 5. Fix 4 — the servicing-operation lifecycle actually moves

`IServicingOperationStore` gained `TransitionAsync(operationId, status, claimGeneration)` and `FindAsync`. No workflow engine was added. The P1 issue path now drives:

```
Prepared → Executing → { Completed | AwaitingExternal | NeedsReconciliation | Rejected }
```

Every transition preserves OperationId, OrderId, the current ClaimGeneration and `UpdatedAt`. Transitions **enlist** in the caller's unit of work so they commit with the same transaction as the Order/document effects, respecting the P0.6 write boundary.

## 6. Fix 5 — the command receipt no longer stays Pending forever

`ICommandReceiptStore.SetStatusAsync` was added, using the existing enum vocabulary only:

`Completed` on full success · `Rejected` on a safe definitive rejection · `Pending` while the provider is still working · `Unknown` on provider uncertainty · `NeedsReconciliation` on a partial irreversible outcome.

No new receipt aggregate and no result-payload storage were introduced: replay derives the authoritative business result from the persisted Order, document and operation state.

## 7. Fix 6 — claim resolution only at a safe terminal state

The claim is resolved **only** on `Completed` or on a rejection that occurred before any irreversible document. It is deliberately retained for `Pending`, `Unknown`, partial issuance and `NeedsReconciliation`. P0 fencing is unchanged: a recovering worker acquires a newer generation for the same OperationId, and a stale generation still cannot finalize.

## 8. Fix 7 — no trusted identity is silently narrowed to 0

`ownerAirlineId > int.MaxValue ? 0 : (int)ownerAirlineId` is removed. `ElectronicTicket.IssuerCarrierId` and `DocumentIssuanceRequest.IssuerCarrierId` now use the authoritative platform type (`long`, matching Core `OperatorSettings.HomeAirlineId`), so **no conversion exists at all** — nothing can be substituted. Migration `P11IssuerCarrierIdentity` widens the column to `bigint`. No platform identifier was redesigned.

## 9. Fix 8 — EventOrdinal foundation

`CommercialEventSequence` (Domain `_Shared/Versioning`) numbers the facts of one accepted commercial mutation from 1 and resets on `IncrementCommercialVersion`. `EventOrdinal` was added to the six commercial domain events and to the five Ordering integration events that already carry `CommercialVersion`, mapped through the existing publish handlers — no change to the shared `BaseIntegrationEvent`, no event sourcing.

Invariant: one mutation ⇒ one `CommercialVersion` shared by all its facts, ordinals `1..K`; the next mutation increments the version and restarts at 1. Non-commercial reservation/document evidence emits no commercial fact and does not advance the version. The sequence is per-mutation in-memory state; each request loads a fresh aggregate and performs one mutation.

## 10. Additional defect found and fixed while testing

`DocumentStockRepository` eagerly loaded **every** allocation of a stock in order to issue one ticket. In the suite this grew unboundedly and produced 30-second SQL execution timeouts. `GetActiveAsync` was replaced by `GetActiveForOperationAsync(ownerAirlineId, documentType, operationId)` with a filtered include, which is both the fix and a real scalability improvement — `Allocate`, `FindAllocation`, `MarkIssued` and `Retire` all work per `(operationId, role)`, so nothing else is needed.

Three test-side defects were also corrected: the deterministic adapter parsed the traveler from the wrong segment of the provider key; the harness seeded a new active stock per test with a colliding random prefix; and the fixture now clears document/stock state once per run so the dedicated test database is reproducible. One test expectation was wrong (a stale generation against an already-resolved claim correctly yields 2701, so the test now targets a still-unresolved operation and asserts 2702).

An earlier apparent 14-test failure was traced to my own chained `dotnet build -o <temp> && dotnet test` command mixing build outputs — not a product defect.
