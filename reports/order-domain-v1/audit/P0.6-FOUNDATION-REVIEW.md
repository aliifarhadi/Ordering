## 1. Claim-generation fencing (review item 1)

### Defect

`OperationClaimStore.AcquireAsync` incremented `Generation` on a tracked row and saved. With no concurrency token, two recovery workers for the **same** `OrderId` **and the same** `OperationId` could each read generation *n*, each write *n+1*, and both believe they owned the current fencing generation — a last-writer-wins update, invisible to the caller. The pre-existing tests only proved contention between *different* operation ids, which the filtered unique index already covered.

### Fix — the existing AeroTech/EF concurrency convention, nothing new

`OperationOrderClaim` gained `[Timestamp] byte[] RowVersion`, mapped with `IsRowVersion()` — the same optimistic-concurrency mechanism `Framework.Core.Domain.Aggregates.AggregateRoot` already uses. The generation increment now fails with `DbUpdateConcurrencyException` for the losing worker, which is translated to `OperationClaimConcurrentlyAcquired` (**2706**, HTTP 409). The losing entity is detached so the caller's context is not left holding a phantom generation.

The first-acquisition race is unchanged in mechanism (filtered unique index) but now distinguishes its two outcomes: a *different* operation holding the claim is `OperationInProgress` (2700); the *same* operation losing the insert race is 2706.

No distributed-lock framework was introduced. Migration: `P06ClaimConcurrencyToken`.

### Proof — `tests/…/Operations/ClaimFencingTests.cs`

| Test | Proves |
|---|---|
| `Two_recovery_workers_for_the_same_operation_cannot_both_own_the_current_generation` | two independent `DbContext`s recovering the SAME `OperationId` concurrently: exactly one succeeds, the other gets 2706, the stored generation is 2, and the winner's returned generation equals the stored one |
| `Only_one_blocking_claim_survives_concurrent_same_operation_first_acquisition` | six concurrent first acquisitions leave exactly one blocking claim row |
| `A_worker_that_lost_the_race_fails_the_generation_check` | the superseded generation is rejected by `EnsureCurrentGenerationAsync` (2702) |
| `A_stale_generation_cannot_resolve_the_claim_after_a_newer_worker_took_over` | a stale generation cannot release the claim, and the claim stays blocking |

## 2. Receipt → operation → claim composability (review item 2)

### Defect

`OperationClaimStore.AcquireAsync` required an `operationId` that no caller could obtain, while `ServicingOperationStore.PrepareAsync` allocated its own id internally and demanded a `claimGeneration` that could only come from a claim taken with an id it had not yet created. The lifecycle could not be composed without a temporary or duplicate identity.

### Fix

The **`CommandReceipt` is the allocation point**. `CommandReceiptStore.AcquireAsync` now allocates the stable `OperationId` (via the platform `IIdGenerator`) when it creates the receipt, and `CommandReceiptResult.OperationId` became non-nullable. A replay of the same key returns the same receipt **and the same `OperationId`**.

`IServicingOperationStore.PrepareAsync` now takes the `operationId` instead of allocating one, and is idempotent: if the operation row already exists it refreshes the claim generation and returns the existing record rather than creating a second economic operation. A concurrent insert of the same id resolves to the winner instead of faulting.

The composed order is now: `AcquireAsync` (receipt + stable OperationId) → `claim.AcquireAsync(orderId, receipt.OperationId, lease)` → `PrepareAsync(receipt.OperationId, …, claim.Generation, receipt.ReceiptId)`.

`ServicingOperationStore` no longer depends on `IIdGenerator`.

### Proof — `tests/…/Operations/FoundationLifecycleTests.cs`

`One_command_resolves_to_one_receipt_one_operation_and_one_blocking_claim_across_recovery` runs the full path twice with the same idempotency key and asserts: the second pass is a replay; the same `ReceiptId` and the same `OperationId`; claim generation advances 1 → 2; and the database holds exactly one receipt, one servicing operation and one blocking claim.

`A_duplicate_request_body_conflict_creates_no_second_operation` proves that the same key with a different body raises 2703 and creates neither a second receipt nor a second operation.

## 3. Persistence transaction boundaries (review item 3)

### Defect

The foundation stores called `SaveChangesAsync` directly on the **scoped** `OrderingDbContext`. Any Order/domain mutation a caller happened to have tracked would have been committed by that call. Economic correctness depended on a developer remembering to invoke these methods only while the context was clean.

### Fix — an explicit, enforced boundary; no second UnitOfWork

`OperationsWriteBoundary` (internal to `Persistence/Operations`) runs `DetectChanges` and refuses the write when any tracked Added/Modified/Deleted entity comes from the **`AeroTech.Ordering.Domain` assembly**, raising `OperationsWriteBoundaryViolated` (**2707**, HTTP 500) naming the offending types. All three stores call it.

The check targets *domain* state deliberately, not "anything else". The inbox marker and outbox rows are required by `04` §12 to commit **together** with the effect, so blocking them would break the SV-017 atomicity guarantee that P0 established. Durable economic intent therefore still commits before any irreversible provider dispatch, while commercial finalization continues to go through `OrderingUnitOfWork`.

### Proof

`Pending_domain_state_cannot_be_committed_by_a_receipt_write` and `…_by_a_claim_write` track a real `ProviderInteraction` aggregate, then assert 2707, the offending type name in the message, and that the aggregate was **not** persisted. `An_inbox_marker_may_still_commit_together_with_a_foundation_write` proves the permitted case still works.

## 4. Caller-scope isolation against the live Identity contract (review item 4)

### Evidence — the actual issuer, at `E:\Projects\DotAir\IdentityServer`

| Source file | What it fixes |
|---|---|
| `TokenIssuance/IdentityTokenClaims.cs` | claim names |
| `TokenIssuance/PrincipalTypeTokens.cs` | `principal_type` is emitted as **snake_case tokens**: `human`, `travel_agency_api`, `internal_service`, `platform_automation` |
| `RestApi/V1/_Shared/ProtocolTokenPrincipalBuilder.cs` | `authz_surface` = `token.AuthorizationSurface.ToString().ToLowerInvariant()`; `context_type` = `context.ContextType.ToString()` (PascalCase); `sub` is written for **every** principal including machines; `travel_agency_office_id` is the **single selected** office; `service_code` is written for a Service context |
| `AegisProjection/Contracts/AuthorizationContextKey.cs` | the platform's canonical business-context key **requires the office** for a travel agency (`travel-agency:{id}:office:{id}`) and allows one for PartnerApi |

### Defect A — `principal_type` was never parsed correctly

P0 used `Enum.TryParse<PrincipalType>(value, ignoreCase: true)`. Against the real wire values only `human` happens to match the C# name `Human`; `travel_agency_api`, `internal_service` and `platform_automation` **never** match their `TravelAgencyApi` / `InternalService` / `PlatformAutomation` names. Every machine principal therefore resolved `PrincipalType = null`.

Fixed by `ServiceHost/CallerContext/PrincipalTypeTokens.cs`, mirroring the issuer's own token table. `authz_surface` (lowercase) and `context_type` (PascalCase) are confirmed to parse correctly with `ignoreCase: true` and are now pinned by tests rather than assumed.

### Defect B — the selected agency office was dropped from `CallerScope`

P0's `CallerScope` used `AuthorizationContextScopeKey.TravelAgency(agencyId)` only. One subject in agency 11 / office A and the same subject in agency 11 / office B collapsed into one caller scope, so one office could replay the other's idempotency key.

Fixed by reusing the **existing** `AuthorizationContextScopeKey` vocabulary — no new key format was invented:

| Context | Scope segment |
|---|---|
| Airline | `AirlineOffice:{id}` |
| TravelAgency | `TravelAgency:{id}+TravelAgencyOffice:{id}` — the office is **required**, matching Identity's canonical key |
| Individual | `Individual:{id}` |
| PartnerApi | `PartnerApiAccessProfile:{id}` (+`TravelAgencyOffice:{id}` when the token carries one, matching Identity's optional office) |
| Service | `Service:{service_code}` — required |
| Global | `Global` |

A context whose identifying claim is missing is rejected with `CallerContextIncomplete` (2705) rather than collapsed.

### Defect C — the principal segment discarded the subject for machines

P0 keyed machine principals on `client_id` alone. `client_id` is **not** written by Identity's principal builder (it may be added by OpenIddict, which the Ordering side cannot assume), while `sub` always is. The principal segment is now `Subject:{sub}`, extended to `Subject:{sub}+Client:{client_id}` when the credential claim is present — never less isolating than before, and never dependent on an unproven claim.

### Contract change

`ICallerContext.TravelAgencyOfficeIds` (a collection copied from Aegis, which reads *grants*) was replaced by `long? TravelAgencyOfficeId`, the single **selected** office a token actually carries, and `string? ServiceCode` was added. Keeping an unused collection alongside a selected-office concept is what allowed the office to be silently dropped.

### Proof — the real `ClaimsPrincipal` adapter, not only the fake

`tests/…/CallerContext/ClaimsCallerContextTests.cs` builds real `ClaimsPrincipal`s from the issuer's literal claim strings: all four `principal_type` tokens; an explicit test that a **C# enum name is rejected** as a principal-type token; all six lowercase `authz_surface` tokens; all six PascalCase `context_type` tokens; airline-backoffice, agency-otapanel (including two offices producing different scopes), individual-ibe, partner-api credential and internal-service scopes; `sub` mapped to `ClaimTypes.NameIdentifier`; and an unauthenticated principal. `CallerScopeTests` adds agency-office, partner-api-office and service-code isolation and the fail-closed cases.

### No BLOCKED_DECISION was needed

The shared contract enums and the live implementation agree on *meaning*; they differ only in *wire spelling*, which the issuer itself defines in `PrincipalTypeTokens`. Ordering maps that vocabulary at its boundary adapter and invents no third representation.

## 5. Ambient-transaction cleanup (review item 5)

### Defect

The non-ambient path detached the query context's transaction in a `finally`; the caller-owned path did not. A scoped `OrderQueryDbContext` could remain associated with a transaction the caller had already committed, rolled back or disposed.

### Fix

Detachment moved into `SaveBothAsync`, so **both** paths release the association in a `finally`, guarded by a `CurrentTransaction is not null` check. One physical SQL transaction across command + local projection is preserved.

### Proof — `tests/…/Synchronizer/SharedTransactionTests.cs`

`A_caller_owned_transaction_leaves_no_association_after_commit` (asserts detachment both inside and after the ambient scope), `…_after_rollback`, and `The_scoped_query_context_is_reusable_after_an_external_transaction_ends` — which rolls back an external transaction and then reuses the *same* scoped contexts for a second successful save, asserting the discarded row is absent and the new one present. The pre-existing `Both_contexts_end_up_on_one_physical_connection` and `A_caller_owned_transaction_governs_the_commit` remain green.

The pre-existing legacy `Domain` → `AeroTech.Messages` coupling (finding F-6) was not enlarged and was not cleaned up here.

## 7. CommercialVersion test assumptions (review item 7)

Binding rule restated: `CommercialVersion` advances exactly once per accepted, committed **commercial** mutation; operational evidence, payment facts, document facts and projection-only changes do not.

### Change made — tests only, no lifecycle redesign

`Expiry_advances_the_commercial_version_exactly_once` was **removed**. Reaching a time-to-live timestamp is a constraint/evidence condition; the legacy poller-driven `Order.Expire` invents a commercial expiry outcome from a clock reading, and P0 must not freeze that as a target invariant.

No test asserts remark edits as commercial mutations (none ever did). A test asserting the opposite was drafted and discarded because, against the legacy code, it could only have been written as a vacuous `>=` assertion — a test that cannot fail is worse than no test.

Retained, because they state the binding rule correctly: create = 1; reservation, payment and document-issue outcomes do not advance; cancellation advances exactly once; a rejected command and a no-event transition do not advance; the emitted events carry the version their mutation produced.

### Legacy methods left in place but explicitly **non-normative**

| Method | Legacy behaviour | Status |
|---|---|---|
| `Order.Expire` | advances `CommercialVersion` on passive time-limit expiry | not a target invariant; replaced when time limits (`01` §9) are implemented |
| `Order.AddRemark` / `ModifyRemark` / `DeleteRemark` | advance `CommercialVersion` | not a target invariant; a remark is an annotation, not necessarily a commercial mutation |
