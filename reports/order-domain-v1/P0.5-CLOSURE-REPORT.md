## 2. Implementation choice — preferred integration order item 1

Core **already exposes** the fact through an approved Service2Service read contract, so no new Core
contract was designed and **no handoff was required**:

```
GET Service/v{version}/OperatorSettings?modifiedAfter=...   →   ApiResult<OperatorSettingsSyncDto[]>
```
`Core/src/Presentation/AeroTech.Core.RestApi/V1/OperatorSettingsAggregate/Controllers/ServiceController.cs`

Ordering consumes it through its **existing** Core reference-data pull-sync mechanism — the same
`ICoreClient` + `ReferenceSyncerBase` + `Syncer/v1/...` pattern already used for customers, currencies,
airlines, cities and airports. The DTO fits `ISyncSourceDto<long>` unchanged.

Resolution path:

```
Core.OperatorSettings (ScopeKey = HOME_OPERATOR)
  → GET Service/v1/OperatorSettings            (existing Core contract)
  → OperatorSettingsSyncer                     (existing ReferenceSyncerBase pattern)
  → ReferenceData.OperatorSettings             (local projection, unique index on ScopeKey)
  → IHomeOperatorProvider                      (Domain port)
  → ReferenceDataHomeOperatorProvider          (ServiceHost adapter, alongside ClaimsCallerContext)
  → CommandReceipt.OwnerAirlineId / ServicingOperation.OwnerAirlineId
```

Only the minimum field set is projected (`Id`, `ScopeKey`, `HomeAirlineId`, `LastUpdateTime`); Core's
default currency, language and time-zone settings were deliberately **not** copied in. `ReferenceData`
keeps its zero project references, so its isolation rule is intact.

**Fail-closed:** a missing or non-positive home operator raises `HomeOperatorNotProvisioned` (**2710**,
HTTP 500). No `0`, no `1`, no `TenantId`, no carrier or caller-context fallback.

**No per-command Core call:** the provider reads one indexed local row; Core is contacted only by the
operator-triggered syncer, exactly like every other reference resource.

**Tenant semantics untouched:** `BaseIntegrationEvent.TenantId` and `IntegrationEventOptions.TenantId = 1`
were not modified. An automated source scan now fails the build if any code conflates `TenantId` with
`OwnerAirlineId`/`HomeAirlineId`.

Also completed, because `BD-1a` was the only thing blocking them in P0: `CommandReceiptStore` (replay
returns the original receipt; same key with a different payload is a 2703 conflict) and
`ServicingOperationStore` (durable `Prepared` intent). Neither entry point accepts an owner, tenant,
carrier, seller, agency or office parameter, and that is enforced by test.
